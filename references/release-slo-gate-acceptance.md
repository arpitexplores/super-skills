# Release and SLO gate acceptance

Use after reading the complete selected workflow for material infrastructure, backend, mixed-workload testing or release decisions (typically 9.4, 4.3 or 5.1; 9.1 owns launch decisions). Apply only relevant criteria. It is acceptance guidance, not a deployment engine, monitoring integration, automatic rollback policy or substitute for real authorised operations.

## Build and start contract

- Identify the approved commit, lockfile and package-manager version, build command, expected generated artefact, actual runtime start command, runtime configuration and environment. Verify the artefact that the production command will run exists and is compatible with that command. Compilation, a source-level check or successful package installation alone does not prove production startup.
- Keep preview and production secrets, data destinations and public URLs distinct. Report unrun smoke checks, missing dependencies and unknown production settings as unverified, not passed.

## Monitoring evidence required for a release gate

- Bind each decision to the expected release ID, service, environment, traffic scope, metric definitions, UTC time window and freshness limit. Reject a sample from an earlier version or a stale window even if its numeric value appears healthy.
- Require present, parseable **finite numeric** measurements. Missing series, empty arrays, malformed values, `NaN`, infinity, unexpected labels, timeouts and partial telemetry cannot produce a green gate. A shell command exiting zero is not evidence the underlying metric is valid.
- Define the numerator, denominator, units, sample window and minimum traffic. For request error ratio, compute `matching_error_requests / matching_total_requests` over the same interval and label set. A counter rate in errors/second is **not** a percentage; compare rates only when both numerator and denominator rates are compatible. Do not divide by zero. A low-traffic window is **insufficient evidence**, not success.
- Validate and aggregate every relevant series for the intended release. Never inspect only the first response series while silently ignoring other instances, regions or status groups. If labels or series are missing, report coverage and block or escalate according to the approved policy.
- Define alert thresholds, duration, minimum observations, owners and an override/hold policy before promotion. A healthy readiness HTTP response alone does not establish error budgets, functional journeys, data compatibility or safe rollback. Avoid automatic rollback on an unqualified generic health check.

## Recovery and rollback contract

- Verify whether the previous application artefact can still read/write the **current** schema, credentials and external contracts. An incompatible migration or destructive data change can make rollback unsafe even when the old image starts.
- Where rollback is unsafe, block it and use an approved forward-fix, compatible restore, tested backup or other recovery plan. Name the decision owner, data-loss/risk conditions, dependencies, RTO/RPO where relevant and what approval is required.
- After an authorised recovery, verify the actual restored release/version, health, safe data state and at least one critical user journey. Report what was inspected versus what was only proposed; do not assert recovery from a plan.

## Small synthetic Super Skills-only fixture

Use mock responses and in-memory data, without contacting a real provider or writing files. Choose a simulated release `release-B`, a known expected build artefact and runtime start command, an error ratio threshold of 1% and a minimum of 100 representative requests over a recent approved interval.

1. Valid `release-B` data with 2 matching errors / 500 matching requests gives 0.4% and may pass the telemetry criterion only if freshness, coverage, artefact and all other required checks pass.
2. Empty results, missing denominator, zero traffic, 20 requests below the minimum, `NaN`, infinite values and a response with one healthy series plus another unhealthy series must **not** pass.
3. Numeric data for `release-A` or outside the allowed freshness window must block promotion of `release-B`. Error-counter rate `2 per second` must not be mistaken for `2%`.
4. A green health response with a missing build artefact or a runtime start command that expects a different output must not pass release acceptance.
5. Simulate a new incompatible schema after `release-B`. Rollback to `release-A` must be blocked until a compatible recovery path and owner are defined. Record the expected restored version, data checks and one critical journey as outstanding verification, not as an executed restore.

Classify each check as passed in the **synthetic fixture**, failed, blocked, not applicable or unverified. Real CI execution, provider telemetry, alert delivery, deployment promotion and recovery/restore remain unverified unless separately authorised and observed.

## Material capacity and workload isolation

- Record demand by journey and tenant/workload class: normal, growth, spike, arrival rate, mean service time, latency/error objectives, bytes, compute/memory, DB read/write/lock/I/O demand, quotas, cost and recovery. Separate measured sustainable capacity, provider hard limits, proposed quotas, assumptions and headroom. Estimate mean in-flight work as arrival rate × mean time in system only under stable conditions; not a tail-latency or spike guarantee. Distinguish registered accounts, active users and offered requests.
- For every shared database, budget maximum physical connections across API replicas, background workers, overlapping revisions, failover and operations reserve. Distinguish pooler client limits from server sessions, check driver/version compatibility, pool waits, locks, query plans, memory, CPU, I/O, replica lag and hot partitions. Logical pools alone do not isolate shared compute. Set class/tenant quotas, deadlines, retry budgets, admission and backpressure; protect critical work, prevent starvation, shed optional work honestly. Scale the bottleneck only with downstream headroom. Use separate resources only when justified.
- Model queue arrival/service rate, oldest age and backlog, drain time after arrivals fall (backlog / (service rate − continuing arrival rate) only if positive and rates stable), worker resource cost, lease expiry and retries. Observe accepted versus rejected work; retain durable accepted effects. Quantify storage growth, direct/streamed upload bandwidth, processing capacity, object operation/transfer costs and expiry. No universal utilisation target, number of queues or database per tenant.
- Example only: 100 usable DB sessions including 10 reserved for operations; 4 API replicas × 12 and 3 workers × 8 = 72 caller sessions, 82 including reserve. A rolling release adding 4 API replicas produces 130 total: unsafe unless overlap or pool limits are reduced or capacity justified. This is a ceiling, not measured throughput. 100 restaurants × 30 images × 4 MB = 3,000 images and 12 GB decimal before derivatives/retries; 30 slots × 1/2 s per image = ideal 15 images/s and 200 s for a ready backlog with no continuing arrivals. Actual service time, variability, transfer, database contention and provider limits must be measured.

## Mixed-load, durable effects and file acceptance

- Define baseline and simultaneous critical/background workloads, tenant spike/fairness, deployment overlap, failure and drain/recovery as applicable. Set separate per-journey/tenant thresholds, allowed rejection, minimum representative samples, time window, correctness invariants and abort/spend limits before testing. Use open arrival profiles for independent demand and closed user pacing where appropriate. Track offered, accepted, successful, rejected, dropped/interrupted work, assertion execution and sample counts; generator CPU/memory/network/saturation, service CPU/I/O/locks/connections, backlog age, p95/p99, errors and costs. Aggregate-only success, missing series, zero/too-few assertions, inadequate offered load or invalid generator evidence cannot establish a pass. Exclude unapproved third-party traffic. Compare equivalent baselines and report actual scope, not inferred capacity.
- For consequential work specify invariant, authoritative state, short transaction and atomic event/outbox if needed, acknowledgement after durable acceptance/effect per contract, idempotency identity, ordering scope, lease/visibility expiry and partial-batch retry. Test crash after commit before acknowledgement, duplicate/out-of-order delivery, lost acknowledgement and uncertain provider response; reconcile before repeating an irreversible effect. Distinguish received/pending/confirmed states; no exactly-once claim. Preserve accepted order prices/options across concurrent menu changes; 4.4 owns payment authority.
- Classify storage (public, private, pending/quarantined, approved derivative, temporary, backup), ownership and environment. Verify scoped expiring grants, unique keys and actual size/content/decode resource limits, private caching, duplicate/replayed finalisation, expired or wrong-tenant access, interrupted transfer, orphaned metadata/object cleanup and deletion/restore. Do not publish unverified objects, trust MIME/key paths or overwrite accepted/published data inadvertently. Test denied state unchanged and reconciliation; source-folder layout is separate from runtime storage.

## Additional small synthetic acceptance cases

Use these illustrative in-memory cases only when relevant, no real provider calls, live traffic or file writes. Agree actual project thresholds separately. Report expected versus observed and failed/blocked/unverified criteria; an agent's plan is not an executed performance test.

1. During a rolling release use the connection budget example above; critical order/payment traffic competes with bulk image processing from one tenant. Identify unsafe 130-session ceiling, cap lower-priority work without starving others, preserve critical journey criteria and note unknown CPU/I/O/lock headroom. Reject a green aggregate with critical journey breach, missing samples or dropped work; establish measured baseline, mixed load and recovery before capacity claims.
2. A worker commits an order and durable event then crashes before acknowledgement. Duplicate delivery, expired lease, out-of-order or partial-batch failure and uncertain payment response must not create a second order/charge or silently lose accepted work. Describe idempotency, atomicity, retry/reconciliation and evidence; never claim provider behaviour from mocks.
3. An interrupted upload leaves a pending object or orphaned metadata; a wrong-tenant/expired grant, oversized or invalid image and repeated finalisation follow. Deny unauthorised access, validate actual content/limits, reconcile or safely clean pending objects, keep published menu and accepted orders intact, verify recoverability and accurate status. No real storage mutation without approval.
